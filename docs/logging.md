# 日志规范

本规范适用于插件的业务流程、模型调用、持久化和向量索引日志。日志用于了解运行结果和定位问题，内容围绕事件、对象、结果、原因与耗时组织。

## 1. 输出入口

服务端日志统一经 `LivingMemoryLogger` 输出，由 Koishi 提供时间、级别和插件名称。Worker 的业务日志通过主线程日志器输出。

| 接口 | 用途 |
| --- | --- |
| `summary(事件名称, 正文, 级别?, 错误?)` | 中文摘要，默认 INFO，可指定 WARN、ERROR 并附原始异常；字符串正文同行显示，字符串数组正文按行显示，正文函数可读取继承的上下文 |
| `diagnosticSummary(内容生成函数)` | 受 `debug` 控制的中文摘要与内容块；按需读取关联上下文并生成完整正文；空内容块保留摘要，生成函数返回 undefined 时跳过日志 |
| `with(关联字段)` | 复用任务、模型调用等上下文 |

普通进展、结果、警告和错误采用 `summary()`，诊断信息采用 `diagnosticSummary()`。两者统一使用中文事件名和中文摘要字段，原始异常与模型返回内容保持原文。日志格式、完整消息输出和输出故障处理由日志器负责，业务代码负责选择事件与内容。

## 2. 日志级别

级别按事件对当前操作的实际影响选择。

| 级别 | 使用条件 | 示例 |
| --- | --- | --- |
| DEBUG | 理解内部执行过程时需要 | 模型输入输出、工具调用详情、候选筛选过程 |
| INFO | 正常开始、重要阶段结果、完成或主动取消 | Dream 开始、向量准备完成、分组完成 |
| WARN | 存在局部失败、部分完成或服务能力降级 | 某批跳过、记忆保存成功但索引同步失败 |
| ERROR | 当前操作整体失败 | Dream 终止、索引打开失败 |

DEBUG 在本项目指由插件 `debug` 开关控制的诊断日志。诊断摘要与正文统一通过 `diagnosticSummary()` 延迟生成。当前实现将其写入 Koishi 的 INFO 通道，因此开启插件 `debug` 后，控制台仍会显示 `[I]`。

正常业务分支采用 INFO 或仅返回结果，例如检索结果为空、记忆保持原样、管理员主动取消。错误级别由承担该操作结果责任的调用层确定。

## 3. 记录时机与粒度

- 手动长任务记录开始、重要阶段结果和任务终态。快速自动流程优先记录有实际变化的结果。
- 阶段日志在结果可用时输出，汇总处理数量和耗时；耗时较长且具有可用进度的阶段，可在进度有实质变化时更新。
- 一次日志调用表达一个完整事件，多行正文作为同一条消息输出。
- 循环内逐项过程归入 DEBUG，普通日志在批次或阶段结束时汇总。
- 每份信息选择一个主要记录位置。诊断日志补充摘要之外的排查信息。
- 完成、部分完成、取消与失败应准确反映实际结果。持久化成功、索引同步和模型处理分别表述各自状态。

## 4. 中文摘要格式

摘要默认使用单行；长正文或需要分项阅读的结果使用多行。可选功能的附属字段随功能启用而显示，字段直接表达结果。例如，画像注入开启时显示“人物画像：0 字符”，关闭时省略人物画像字段。

单行格式：

```text
事件：Dream 开始; 预设：所长（Character）
事件：Dream 初始分组完成; 生成 6 批，每批最多 30 条，耗时 0.014 秒
事件：记忆注入; 预设：所长（Character）; 会话：群聊 810727721; 记忆快照：127 字符; 人物画像：0 字符
```

Dream 准备阶段统一采用单行摘要：

```text
事件：Dream 向量准备完成; 记忆数量：166 条; 向量模型：讯飞星火/xop3qwen8bembedding; 向量维度：768; 耗时：0.070 秒
```

事件标题使用“对象 + 动作或结果”，例如“Dream 分组完成”“索引重建完成”。正文使用中文字段名、具体数值及单位，采用直接、客观的描述。

Character 的“记忆注入”表示本轮模板变量内容已生成；每轮首次生成成功时记录一次，快照和人物画像长度取实际拼入变量的正文。同轮请求模板与历史模板共用这份结果。

摘要直接展示标题和正文。时间、插件名称和级别由宿主添加；关联 ID 按实际定位需要放入异常或诊断事件。Dream 准备阶段沿用上述精简格式，预设在开始时显示。

## 5. 字段与数值

| 内容 | 规则 |
| --- | --- |
| 数量 | 使用整数并说明对象，如“166 条记忆”“6 批”“61 次交换” |
| 覆盖进度 | 使用“已完成数量/目标数量”，明确统计对象 |
| 耗时 | 摘要以秒为单位并保留三位小数 |
| 得分 | 摘要保留两位小数，注明评分含义 |
| 比例 | 摘要保留一位小数并带 `%`；基数为零时展示前后值 |
| 内存 | 摘要使用 KiB、MiB 等明确单位，区分估算值与实测值 |
| 模型 | 使用实际配置或返回的模型标识；向量准备同时显示维度 |
| 缺失信息 | 可选诊断字段省略；需要明确呈现的供应商缺失信息写“供应商未返回” |

性能耗时采用 `performance.now()` 的差值。各阶段耗时与任务总耗时分别测量。模型调用耗时包含宿主调用内部的等待和重试，统计名称应体现测量范围。

算法目标值使用实际含义命名，例如“组内近邻得分”。算法得分提升和业务效果分别评价。

## 6. 事件与上下文

所有级别统一采用中文事件名称，使用“对象 + 动作或结果”的格式。正常路径、重试、降级及失败分支采用相同的摘要格式。

通过 `with()` 继承预设、会话、人物、模型、批次及轮次等上下文，调用方选择与当前事件有关的字段。模型重试显示调用序号，批次重试显示批次及轮次。人物画像失败展示人物名称，索引状态使用中文描述。

原始错误保留字段路径、错误码和供应商返回内容；异常对象换行展示完整堆栈及原因链。

## 7. 错误记录责任

错误由决定恢复、跳过或结束操作的层记录。下层保留原始错误并向上传递，上层补充操作对象、实际影响和处理结果。

- 整体失败由任务或服务入口记录终态错误。
- 局部失败由负责恢复或跳过的层记录 WARN；任务终态汇总部分完成情况。
- 原始异常通过日志器的错误参数传递，以保留堆栈和原因链。
- 重试过程放在 DEBUG；最终结果由持有操作生命周期的层记录。
- 纠错日志针对模型解析、参数及明确的业务校验失败；内部代码和存储故障向任务入口传播，由任务失败日志报告。
- 内层详细错误与外层任务汇总各自承担不同信息：详细错误解释原因，任务汇总说明整体结果。

例如，记忆已保存而索引同步失败时，WARN 应同时写明保存结果、索引影响及实际恢复入口。恢复时间只依据已有机制描述。

## 8. 模型与工具日志

结构化结果解析失败采用“阶段名称＋结果解析失败”的中文诊断摘要，展示预设、适用的会话与人物、调用序号和原始校验原因。

模型请求和响应复用 `model_calls.ts` 的封装。提示词、记忆正文、来源消息、模型原文及完整工具参数放在 DEBUG 内容块中，按实际请求边界记录。

召回快照保存成功后，更新摘要与完整快照正文合并为一条 INFO 日志，始终显示。正文以 `========召回快照========` 分隔。

模型输入采用中文摘要，头部展示业务阶段、模型及适用的预设和会话；逐次打印提示词的流程附加调用序号。正文按系统、用户、助手和工具等角色分段，标题采用 `========系统消息========` 的形式，段间空一行，完整保留消息内容。失败摘要使用模型、作用域和调用序号定位。

每次模型调用前输出单行中文诊断摘要，展示模型、调用序号及适用的预设和会话，例如：

```text
事件：召回模型调用; 模型：ollama/gemma4:31b; 调用序号：1; 预设：所长（Character）; 会话：群聊 810727721
```

调用序号取当前业务阶段的模型调用计数：召回中包括工具循环的后续调用，结构化输出中包括纠错调用。宿主内部的 HTTP 重试位于同一次模型调用内。召回输入正文沿用首次调用记录策略，后续调用由逐次请求状态和响应日志反映。

模型响应按各流程的文本记录策略生成内容块，有可展示的内容块时输出摘要及正文。摘要展示模型、预设和会话。工具调用以 `========工具调用========` 分段，下一行采用 `living_memory_search:call_0` 的形式，随后输出完整参数。召回关闭模型文本记录，纯文本响应由后续快照更新、沿用当前快照或失败日志体现结果。

会话历史采用增量记录：系统输入、批次输入和反馈在加入会话时记录。供应商用量由业务流程按需读取。一次宿主模型调用与底层 HTTP 请求次数分别统计。

普通日志展示数量、模型、状态和耗时。凭据留在配置与请求处理边界；结构化日志沿用日志器的凭据字段脱敏。摘要和任意文本的内容由调用方选择，字段脱敏只覆盖结构化字段。

## 9. 应用范围与维护

记忆提取数量由协调层在保存完成后记录为一条“记忆提取完成”中文诊断摘要，沿用 `debug` 开关。跳过提取和解析失败由各自的结果日志记录。

本文件是项目约定。正常业务进展和结果采用中文摘要，技术诊断及异常保留结构化关联信息。日志级别以本规范定义为目标，现有调用的级别与格式需结合实际代码逐项确认。

修改日志时核对事件含义、级别、记录责任、字段单位和重复情况，并同步对应业务文档。沿用仓库规定的集中验证时机；只在行为依赖日志内容或日志器格式契约变化时补充必要验证。

## 10. 各流程记录责任

- ChatLuna 在本轮注入内容准备成功后合并记录快照与人物画像长度；接收事件、作用域解析成功和调用协调器前的入队提示由实际处理结果替代。
- 模型响应由响应内容块决定是否输出。普通业务摘要独立于附属正文，搜索零结果仍显示匹配数量。
- Dream 会话输入、反馈、工具结果及画像处理保留 debug 控制，正文采用中文分段。批次完成为 INFO，跳过批次为 WARN；任务完成、部分完成、失败分别为 INFO、WARN、ERROR。
- 索引任务开始和完成使用中文 INFO 摘要，任务失败使用 ERROR 并保留原始异常；服务层继续记录索引可用状态。
- Reranker 降级以 WARN 说明沿用混合检索排序，并保留实际模型和异常。

功能开关关闭时，在入口静默结束。等待、跳过和配置异常提示只面向已经开启的功能；共用基础能力按实际使用方继续运行。

### 统一输出格式

所有入口使用同一套输出规则：头部为“事件：名称; 字段：值”，字段之间使用分号；内容块标题为 `========标题========`，块间空一行，正文完整显示。内容块与消息头共用字段格式。技术事件保留稳定事件代码和关联字段名，展示格式与中文业务摘要一致。空内容块保留事件摘要，模型空响应由模型日志调用方主动跳过。

提取原因及具体记忆正文由模型工具调用日志记录，提取完成摘要只显示预设、会话和数量。带异常的日志在摘要后换行，下一行展示完整异常与堆栈。
