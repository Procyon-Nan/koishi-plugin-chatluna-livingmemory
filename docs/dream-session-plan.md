# 全量 Dream 会话化执行方案

日期：2026-10-19。

状态：用户已批准会话化与配套结构重构，按批实施，每批审查后由用户手动提交，再继续下一批。第 8 节为上下文缓存的源码核查与实现约束，不代表已验证真实供应商缓存命中。

本次改造直接替换并移除旧 Dream 实现，不保留旧执行协议、兼容入口或降级路径。不得以兼容旧增量为理由保留旧代码，也不得为新旧并存提取共享抽象。第 3、4 批合并交付，新入口接入与旧实现删除同时完成。

本文件记录本次讨论的最终决定。早期 `tmp/` 下的 Dream 草案和上下文交接文件仅作背景；与本文冲突的部分以本文为准。

## 1. 目标与范围

将手动全量 Dream 从“每个整理单元独立调用模型、一次返回整组操作”改为连续的 Agent 会话。模型调用记忆工具，程序根据实际处理状态自动推进批次。

- 仅修改 LivingMemory，不修改 ChatLuna。
- 全量检查本次开始时选定的全部活跃记忆，包括已固化记忆。
- 沿用 `DreamClusterer.buildClusters()` 的分区、HDBSCAN、噪声整理和超大簇切分；每批最多 30 条。
- 沿用现有系统提示词的角色、人设、事实约束和整理原则，只调整执行协议。
- 以本地现有数据验证，不围绕假设的一万条记忆另设架构。
- 增量 Dream 留待之后重新设计，本次移除旧增量执行链及其自动触发装配，不保留旧实现作为兼容路径，也不将自动增量触发改为自动全量执行。旧 `DreamUnitProcessor`、`DreamExecutor`、操作数组 schema 和 `applyDreamMerge()` 随生产切换一并删除。
- 暂不拆分 `src/service/persistence/entries.ts`。
- 活跃记忆至少 30 条的触发门槛、预设隔离、Dream 任务串行和用户画像开关继续有效。
- 不新增断点续跑、持久化会话历史、主题树或新的聚类算法。

已提交的基础工具：

- `a2ea469`：`living_memory_merge_memories`，至少两个不同来源 ID 合成一条新记忆，原子归档全部来源，不指定 target。
- `44047e1`：`living_memory_checked_memory`，批量确认无需改动的记忆，必填非空 `reason`。

## 2. 执行器与状态所有权

LivingMemory 自行管理会话循环，复用 ChatLuna 公开导出的 `createOpenAIAgent` 执行每轮模型决策，使用公开模型接口发起独立的历史摘要调用。第三批实际接入时确认 `compressChunk()` 未通过 ChatLuna 包导出，无法供插件正常导入；因此调整为同样的摘要调用方式，不访问包内私有路径，也不修改 ChatLuna。不使用 `AgentRunner` 的完整循环，也不访问或改写其内部状态。

一次任务持有以下状态，任务结束后释放：

| 状态 | 含义 |
| --- | --- |
| `targetMemoryIds` | 本次全量检查的原始活跃记忆范围 |
| `availableMemoryIds` | 已通过批次、检索或操作结果提供给模型的记忆 ID |
| `processedMemoryIds` | 本次已经成功处理的记忆 ID，用于覆盖统计和跳过重复发批 |
| 批次列表与当前位置 | 沿用已有整理单元，决定下一批 |
| 会话历史与当前批次起点 | 维护连续交互，并划定压缩边界 |
| 本批模型轮数、连续无效轮数 | 控制纠错与跳过 |
| 操作统计与失败记录 | 生成任务状态、详情和诊断日志 |

当前批次待处理项由“当前批次 ID 减去已处理集合”计算，不再维护一份独立待办计数。

`processedMemoryIds` 不是修改锁。已经处理过、但仍活跃的记忆允许在后续批次再次更新、合并或归档。重复操作不重复增加原始目标的覆盖数量。

新合成记忆不自动追加为本次待检查批次，但加入可访问范围，可以在后续继续处理。任务运行期间自动提取的新记忆不自动扩大本次目标范围。

## 3. 工具与成功语义

会话经 `src/service/memory/tools/index.ts` 的统一创建入口取得检索、来源消息查询、更新、合并、归档和检查工具。沿用现有工具参数、应用接口和写入约束，不新增独立创建记忆的整理操作。

| 成功操作 | 覆盖记录 | 固化处理 |
| --- | --- | --- |
| `checked_memory` | 确认的 ID | 对应活跃记忆设为已固化 |
| 更新 | 目标 ID | 更新后的活跃记忆设为已固化 |
| 合并 | 所有来源 ID | 新生成的记忆设为已固化 |
| 归档 | 归档的 ID | 不再作为活跃待处理记忆 |

- 固化由 Dream 执行层负责，检查工具自身不承担持久化职责。
- 成功记录来自实际工具执行结果，不从模型自然语言或诊断日志推断。
- 事实已经提交、仅索引同步产生警告时，记录成功操作及警告，沿用后台对账。
- 失败或未处理记忆保留原有固化状态，不批量重置旧状态。
- 批次失败不回滚其中已经成功的操作和固化。
- 同轮多个工具按模型返回顺序串行执行，整轮结束后再判断批次完成情况。
- 保留可解析的原始模型消息、工具调用 ID 和供应商相关元数据；一轮 assistant 工具调用消息只记录一次，并配齐相应工具结果。解析器拒绝的响应作为转义后的纠错数据追加，不重放损坏的调用消息，也不伪造工具执行结果。
- 检索结果加入可访问范围，但检索本身不计为已处理。

应用写入继续经过预设队列和仓库事务。新增的固化衔接必须区分“事实写入失败”和“事实已提交但索引未同步”，避免重复执行已经提交的合并。

## 4. 批次推进与结束

```text
读取本次活跃记忆并调用现有 buildClusters()
  ↓
建立固定系统提示词、固定工具集合和任务会话
  ↓
取下一整理单元，去掉已处理 ID，追加完整记忆输入
  ↓
调用前检查最近一次供应商上报的输入用量；达到 200k 则压缩更早批次
  ↓
模型决策 → 串行执行工具 → 记录成功结果及固化
  ↓
本批全部处理完成？
  ├─ 是：发送下一批；无下一批则结束整理
  └─ 否：继续本批；达到失败或轮数限制则记录遗漏并进入下一批
  ↓
执行既有画像生成阶段，汇总任务结果
```

- 空批次直接跳过，不向模型重复发送已覆盖记忆。
- 模型不负责提交“本批完成”，也不负责请求下一批。
- 尚有待处理项时，模型返回普通最终回答不能结束整场任务；程序追加纠错信息。
- 已经完整覆盖目标范围时，以程序状态结束整理，不依赖模型额外宣布完成。
- 每批输入包含记忆的完整模型可见字段，不能只发送 ID 和摘要。
- 当前进度作为新的尾部消息或工具结果补充发送，旧进度消息不原地改写；以最新程序进度为准。

## 5. 纠错与任务状态

初始内部常量：每批最多 60 轮模型决策，连续 3 轮完全无效则跳过。暂不增加配置项。

- 请求失败、全部工具调用失败、尚有待办却提前结束，计为无效轮。
- 正常检索或至少一个工具有效执行，中断连续无效计数；仍计入本批 60 轮上限。
- 不以“本轮覆盖数量没有增加”直接判定失败，因为检索和再次处理已有记忆也可能有效。
- 摘要生成是单独的压缩调用，单独记录用量，不混入模型决策轮数。
- 跳过时记录本批尚未处理的 ID 与原因，并明确告知模型进入下一批。
- 插件停止、任务取消或无法继续的基础设施故障终止整场任务，停止接受后续写入；不撤销已提交事实。

任务终态：

| 状态 | 判定 |
| --- | --- |
| `completed` | 本次目标记忆全部处理完成 |
| `partial` | 遍历结束，部分目标成功处理，但仍有未处理目标 |
| `failed` | 没有目标成功处理，或整场任务因不可继续的故障中断 |

`checked_memory` 属于成功处理。整体中断即使已有成果仍标记 `failed`，详情保留成果和未完成范围。最终遗漏依据结束时的覆盖集合计算；早期跳过的记忆若后续被成功处理，不再算最终遗漏。

保留现有操作统计，另记录目标覆盖数量、跳过批次和未处理 ID，不能把操作次数相加当作覆盖数量。画像生成保持既有开关、位置和错误处理，不因某一批被跳过而取消整个后续阶段。

## 6. 上下文压缩

- 固定阈值为供应商返回的单次输入用量 200,000 tokens，不是任务累计消费量。仅使用决策响应的 `usage_metadata.input_tokens`，不以本地估算或输出用量触发，也不额外叠加缓存计数。
- 每次模型决策前检查最近有效上报值；本轮新增工具结果和批次内容要等下次响应才能反映在供应商用量中，不自行估算增量。
- 用量在响应返回后才可获得；本轮工具全部执行完毕，在下一轮决策前判断是否压缩。因此不能承诺请求发出前恰好卡在 200k。缺失、非有限或非正输入用量不覆盖最近一次有效上报；始终没有有效上报时不触发阈值压缩，不以本地估算补齐。
- 压缩成功后清除已记录的输入用量，等待下一次决策响应上报。摘要请求的 usage 不计入主会话，也不从保留的当前批次旧消息重新读取用量。日志中的 `lastReportedInputTokens` 表示最近有效上报，不表示即将发送的请求大小。
- 系统提示词原样保留。当前批次的完整输入以及本批全部模型、工具交互原样保留。
- 只将当前批次起点之前的历史与已有摘要交给摘要生成；摘要记录整理结论、重要关联、约束、失败情况和待关注事项。
- 不套用宿主 Agent 压缩中工具参数 300 字符、结果 500 字符的截断方式。
- 摘要非空且请求成功后才替换旧历史；压缩失败保留原历史并终止。压缩后的输入大小等待下一次供应商响应确认，不用本地估算判定是否低于 200k。主会话与摘要请求仍用宿主计数检查模型容量，超限时失败以避免宿主静默裁剪当前批次；这项检查不参与压缩阈值判断。
- 单批自身达到 200k 按当前 30 条记忆的场景暂不设计特殊机制，在本地验收时观察。
- 核对实际模型能容纳 200k 输入及输出预算；不能通过静默降低阈值掩盖模型不适用。按宿主声明的上下文容量扣除输出预算，不足 200k 时调用前失败；输出优先沿用明确配置的正数，未限定输出时在本任务调用级设为 4096。实际端点容量仍需真实环境验收。
- 使用调用级 `maxTokenLimit` 避免宿主原有的低输入上限提前裁剪；请求投影仅去掉 assistant 的 `usage_metadata`，防止宿主使用压缩前基线。原始历史保留完整用量，内容、调用 ID、推理块、供应商签名及其他协议元数据继续保留。

## 7. 提示词与完整记忆视图

复用现有 Dream 系统提示词的角色、人设卡片、第一人称表达、事实约束和整理判断原则，仅调整：

1. 从单次提交 `keep/update/merge/archive` 操作数组改为调用实际工具。
2. 无需改动时使用 `checked_memory`，理由由工具 schema 要求，不在正文重复字段定义。
3. 合并使用至少两个来源 ID 生成新记忆，去掉选择和保留 target 的规则。
4. 可操作范围覆盖当前会话已提供的记忆，包括检索结果；不再限定为单簇。
5. 移除“一次输出必须覆盖整批”和“同任务不得再次操作已处理记忆”的规则，覆盖与推进由程序控制。

`src/service/prompts/memory_entries.ts` 继续承担字段渲染。现有搜索视图比 Dream 视图精简，不能直接用它替代完整批次输入。压缩前后均保留 ID、类型、正文、摘要、关键词、情绪、重要性、创建/更新时间及 speaker 标签等原有 Dream 信息。

最终只保留会话式 Dream 提示词。删除旧操作数组协议、target 合并规则及其 schema；人设直接写在唯一的系统提示词构建函数内，不再为新旧流程共用而提取 `buildDreamIdentity()`。完整批次和独立压缩请求按实际发送时机构建；只使用一次的压缩文案直接放入对应函数，一行 XML 包裹复用 `prompt_format.ts`，不再新增专用包装函数。

## 8. 上下文缓存

### 8.1 结论与证据边界

这里指模型供应商的输入上下文缓存，不是插件本地缓存最终回答。插件自行管理循环不会天然破坏供应商缓存；能否命中取决于实际请求前缀、模型、账户/路由、供应商缓存策略和保留时间。

兼容目标覆盖多数具有上下文缓存能力的 adapter，不绑定本地当前选择的 Gemini。采用统一的追加式会话组织，并通过宿主已有调用接口承接不同协议的缓存参数。缓存是否启用、请求能否复用前缀、命中量能否上报是三个独立问题。

当前 ChatLuna 源码及供应商文档核查结果：

| 请求路径 | 缓存接入方式 | 已确认的边界 |
| --- | --- | --- |
| OpenAI Chat Completions / Responses、OpenAI-compatible | 对支持自动缓存的上游保持稳定前缀，沿用宿主缓存键传递 | shared requester 将 `params.id` 写入 `prompt_cache_key`；openai-like 在 `setCacheKey` 未开启时移除它。键不等于启用缓存，兼容协议也不等于上游提供缓存 |
| Gemini | 使用服务端隐式缓存 | 常规 builder 不创建或引用显式缓存对象；`cachedContentTokenCount` 已映射为 `cache_read`。官方文档说明 Gemini 2.5 及之后支持隐式缓存 |
| DeepSeek | 使用服务端默认开启的上下文缓存 | 原生 requester 复用 shared 请求构建；无需为其建立独立缓存客户端。实际命中仍受前缀匹配和服务端持久化影响 |
| Qwen、智谱、豆包等 | 沿用各自 adapter，保留相同的历史前缀 | 已确认这些 requester 使用 shared 请求构建；具体模型、端点是否默认启用缓存须单独核验，不能因请求兼容就宣布全部支持 |
| Claude Messages | 对支持该功能的端点，通过已有 `overrideRequestParams` 传入顶层 `cache_control: { type: 'ephemeral' }` | 当前 requester 默认不添加缓存标记，但会合并请求覆盖参数，并已读取缓存读写量。官方顶层自动缓存机制会随会话推进缓存位置，无需逐条重写消息块 |

Claude 的缓存参数必须限定在已确认支持的请求路径，不能按模型名称猜测协议，也不能广播给所有 adapter。自定义 platform 名称不代表协议类型；若宿主公开信息不足以可靠识别，沿用明确配置的请求覆盖参数，不访问私有字段猜测。旧 Bedrock 路径及未兼容该参数的代理不纳入这一顶层参数方案。

`ChatLunaChatModel.invocationParams()` 接受调用级 `id` 和 `overrideRequestParams`；实现应通过这一公开调用路径传递并保留既有覆盖参数，不修改共享模型对象或全局 adapter 配置。仅把会话 ID 放进 `configurable.agentContext` 不足以证明 requester 收到了它。参数从 Agent 调用传至实际请求的链路需要在实现验收中核对。

不建立供应商 SDK、独立 HTTP 路径或缓存对象生命周期管理。支持自动缓存的上游共用同一会话实现；需显式开启的协议使用最小调用参数差异。使用代理、不同账户或不同上游路由时，不能仅凭本地代码断言实际命中或计费折扣。

### 8.2 必须保持的请求结构

```text
工具定义：本次任务内固定内容和顺序

压缩前：
System：固定的规则与人设
Human：第一批完整记忆
Assistant / Tool：已发生的交互，原样保留
Human：后续批次完整记忆或最新进度
Assistant / Tool：继续追加

压缩后：
System：相同的规则与人设
Human：更早批次摘要（本次压缩后固定，直到下一次压缩）
Human：当前批次完整记忆
Assistant / Tool：当前批次全部交互
后续消息继续追加
```

- 任务开始时确定系统提示词、人设和工具定义，不逐轮插入当前时间、轮数、随机标识或重新渲染的人设。
- 当前进度、剩余 ID、错误反馈和新批次均追加在历史末尾，不能插到既有历史之前。
- 已发送的历史消息不原地改写或删除；记忆被更新后，通过新操作结果提供新内容，不回写先前批次输入。
- 程序内部状态和日志字段可以更新，不应因此改变已发送的模型输入。
- 保留真实 assistant 消息与工具结果，包括工具调用 ID 以及供应商需要的签名等元数据；不重新生成既有调用 ID。
- 在任务内复用已解析的模型和稳定会话标识，但会话标识不是缓存命中的充分条件。
- 不为了追求缓存而省略当前批次字段、忽略更新事实或延后必须执行的压缩。

这修正了此前“每轮提供当前状态”的摆放方式：状态仍然准确提供，但通过尾部追加实现，不在历史前方放一个每轮变化的占位块。

### 8.3 压缩与缓存的关系

正常推进时，尽量让下一请求保留上一请求的输入前缀，并在末尾增加新交互。换批也继续追加，不重置会话。

压缩会将较早历史替换为新摘要，因此旧的长历史前缀不再相同，不能承诺压缩后维持原有长上下文命中。未变的系统提示词和工具部分仍可能复用缓存；摘要及新历史需要按供应商规则重新建立可复用前缀。

摘要生成调用有自己的输入和成本，应与整理调用分别统计，不能假定它命中整理会话的缓存。

### 8.4 验证与可观测性

- 在 LivingMemory 的模型调用日志中读取并记录已有响应的输入 token、输出 token、`cache_read`，以及供应商实际返回时的 `cache_creation`。
- 缺失缓存字段记为“未返回”，不擅自记为 0，也不据此断言没有命中。
- 分别观察同批连续调用、跨批次调用、压缩后首轮与后续调用。
- 验证实际消息和工具定义的稳定前缀，不能仅凭使用相同 conversation ID 就判定缓存保持。
- 不跨 adapter 直接套用 `cache_read / input_tokens`：当前 Claude adapter 原样传递的 `input_tokens` 只包含未缓存输入，完整输入为未缓存输入、缓存读取和缓存创建之和；其他协议可能已经包含缓存部分。只记录 adapter 返回的原始计数，不计算跨协议命中率。200k 直接比较公开模型响应中的 `input_tokens`，不猜测 adapter 或自行补加缓存值；因此不能保证所有 adapter 的这个字段都表示含缓存的完整上下文大小。
- 缓存上报能力也不是统一的：shared OpenAI usage 转换读取标准 `prompt_tokens_details.cached_tokens`；上游若只返回其他自定义字段，可能没有进入标准元数据。缺失统计不妨碍服务端缓存，本项目不因此重写 adapter。
- 分别核对 OpenAI-compatible、Gemini 和 Claude 三类协议的实际序列化请求，涵盖工具往返、换批和压缩；国内 adapter 按真实使用的端点补充验证。不以单个 Gemini 模型的结果代表全部 adapter。
- 不预设固定命中率或费用节省比例。不修改 ChatLuna，不通过修改全局 adapter 配置实现本方案。

参考：[Gemini API Context caching](https://ai.google.dev/gemini-api/docs/caching)、[Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache)，2026-10-19 查阅。实际命中尚待运行验证。

本次将新入口接入与旧执行链删除一并完成，不再安排将旧执行器迁入增量目录的步骤，也不建立兼容转发文件。

会话状态由 `state.ts` 中的任务状态持有，优先采用普通对象和函数。`runner.ts` 决定执行顺序，`history.ts` 独占消息历史与压缩边界，`tools.ts` 将实际执行结果登记到任务状态。不要在工具、runner、job runner 中各保存一份覆盖集合。

检查工具在第 1 批移除直接写入处理集合的耦合，等待注入的检查处理函数完成后才返回。第 2 批由 Dream 为它提供处理函数：先验证全部 ID 的可访问范围，再完成必要的固化，最后登记成功；任一步失败不返回检查成功。其他操作同样通过类型明确的内部结果衔接，不解析面向模型的自然语言来判定成功。事实写入和固化尽量复用同一个既有写入入口，避免产生“事实已成功但固化失败后再次执行合并”的路径。

第 2 批的具体接口衔接：

- `createDreamSessionState()` 保存固定目标集合、批次位置、可访问与已处理集合、操作统计和跳过记录；`nextDreamBatch()` 过滤已覆盖条目，`getDreamCoverage()` 始终按原始目标计算遗漏，不把新增合并结果或检索到的额外记忆算入目标数。
- `createDreamSessionTools()` 经公共工厂选择六个工具，通过注入的查询和变更依赖绑定固定预设。检索登记可访问 ID；来源查询及写入只接受已提供 ID；成功写入登记覆盖。未定义第二套工具类或执行 JSON 解析。
- 应用层 `updateActiveMemory()` 与 `mergeActiveMemories()` 增加可选固化参数，逐层传至现有仓库事务；Dream 传入 `true`，主对话不传，原默认行为保持。更新和合并不再需要后置的独立固化调用。
- `setMemoryConsolidation()` 在预设队列内读取整组 ID，若任何 ID 不存在、跨预设或已归档则在写入前失败。删除增量调用后移除 `requireAllActive` 选项，直接执行整组活跃校验。
- 更新与归档遇到既有 `LivingMemoryFactsCommittedError` 时登记成功，再交给公共工具生成警告；合并继续使用带新 ID 和警告的结果。checked 的处理函数返回警告数组，工具保留 ID、理由和警告，不将索引失败误报为事实失败。
- 来源消息工具改为依赖 `LivingMemorySourceProvider`，主对话注入应用服务，Dream 注入固定预设的来源查询。无需伪造 Koishi Context，也不增加工作流专属的来源消息工具。

第 3 批的具体接口衔接：

- `runDreamSession()` 接收既有会话状态、固定工具、模型、人设、speaker 列表、任务 ID 和取消信号；生产装配与第 4 批合并交付。复用宿主 Agent 每次只做一轮决策，工具按返回顺序串行执行，整轮完成后判断覆盖。
- `DreamSessionHistory` 独占消息、批次起点和最近有效供应商输入用量。`startBatch()` 追加完整批次；`recordUsage()` 在原始响应回调中接收用量，parser 失败也不会丢失上报；`prepare()` 在上报值达到 200k 时压缩更早批次，摘要成功后替换历史并清除用量。压缩失败或首批达到阈值且没有更早批次可压缩时终止，保留已有事实成果。
- 提示词只服务于新会话协议；完整系统规则保持连续可读，批次渲染复用现有字段格式，动态数据经既有格式化函数转义。取消为新旧提示词共用而建立的身份片段和旧协议保留要求。
- 任务 ID 经公开调用参数 `id` 传至 requester，压缩使用独立的 `:compression` 后缀；覆盖参数合并模型既有配置与显式调用参数，不按名称猜协议，也不向所有 adapter 广播 Claude 参数。
- `createLoggedModel()` 增加原始响应回调，用于保留 parser 处理前的消息；模型响应日志记录供应商原始计数及缓存明细，不计算跨协议命中率。日志用 `inputDetails`/`outputDetails` 命名明细，避免通用凭据脱敏误隐藏 token 明细。
- 取消信号在模型调用前后及工具之间检查；明确的向量索引基础设施错误终止整个会话，普通请求或工具失败按既定轮次规则处理。

## 10. 验收标准

1. 现有聚类输出和最多 30 条的上限保持不变，全量仍覆盖已固化的活跃记忆。
2. 同一会话连续处理多个批次，无需模型提交批次完成；成功操作和 `checked_memory` 正确推进覆盖。
3. 已处理活跃记忆可再次参与更新或合并；合并来源覆盖计数正确，新结果不形成无限待办。
4. 部分失败保留成功写入和固化，进入下一批；60 轮与连续 3 个无效轮限制可观察。
5. `completed`、`partial`、`failed` 的数据库结果和前端展示符合定义。
6. 200k 阈值只按供应商上报的单次输入用量触发；199,999 不触发、200,000 触发，本地长历史、输出用量和缓存明细不改变判断；缺失或无效上报不补估算值。
7. 压缩保留当前完整批次和全部交互，压缩后计数不沿用失效的旧 usage 基线。
8. 普通轮次和跨批次均保持稳定请求前缀；覆盖 OpenAI-compatible、Gemini、Claude 三类请求协议，核对调用 ID、按需缓存参数与元数据传递。在实际供应商返回字段时观察缓存命中，区分计数口径，不把结构检查当作真实命中证明。
9. 保留完整工具调用消息及元数据，校验同轮多工具时的消息配对。
10. 旧 Dream 全量与增量执行链、旧操作数组协议及旧合并事务均已删除；主对话工具、预设隔离、speaker 关系、索引同步和用户画像的必要行为保持正确。

实现后的检查：`yarn lint`、`yarn test`、`yarn atsc -p tsconfig.json --noEmit`、`yarn build:client`、`git diff --check`；若触及服务端构建、Worker 或包边界，再执行相应构建。

真实模型验收使用本地现有数据，并将模型请求、记忆写入、缓存命中观察与静态检查分开报告。布局与基础模块批次不发起真实 Dream，不调用真实模型，也不修改运行中的记忆数据。
