# Dream 流程

Dream 是按预设手动触发的后台记忆整理任务。它读取全部活跃记忆，按语义分批，通过持续工具会话完成整理，再生成用户画像。

## 触发与准备

预设至少有 30 条活跃记忆时可以启动 Dream。同一预设同时运行一个任务，重复触发返回已有任务状态。启动时将该预设遗留的运行中 Dream 记录标记为失败，再创建本次任务。

不同预设共用一个分组准备队列；获得执行权后依次完成：

1. 读取全部活跃记忆，包括已固化项，固定本次目标 ID 集合。
2. 创建配置指定的 `mainModel`。模型声明的最大上下文须至少为 200,000 tokens；输入容量使用模型最大上下文，输出参数沿用宿主模型配置。
3. 读取已有正文向量，完成语义分组。

准备完成后释放队列，解析预设人设和用户标签，装配工具并进入会话。不同预设的会话可以独立运行。

## 语义分组

目标是让语义相近的记忆进入同一批。对于 N 条目标记忆，形成 `ceil(N / 30)` 个非空批次，每批 1–30 条，每个目标恰好属于一个批次。

### 向量快照与容量二分

正文按稳定 ID 排序，每页读取最多 256 条已有向量，核对正文 hash、活跃状态、模型、维数和索引 generation，组装连续 `Float32Array` 矩阵。

矩阵通过 `ArrayBuffer` 转移到 Dream Worker。Worker 执行容量约束球面二分：每个节点携带最终批次数预算，依据两个单位中心的语义费用选择合法切点，最多迭代 3 轮，递归形成完整初始分组。分组出口核对覆盖、标签计数和容量。

### 近邻候选与跨组优化

多批次分组自动进入以下阶段，单批次直接使用初始结果：

1. 在初始组中选取分散的至多 32 个探测点，通过向量索引 Worker 查询近邻候选，成功结果继续复用。HNSW 在启动对账或全量重建后由索引维护任务构建，后续任务复用。索引就绪后，由 PostgreSQL 优化器选择 HNSW 或精确扫描取得候选，维护规则见[向量索引](vector-index.md)。
   2001～4000 维向量通过半精度 HNSW 查询候选，构图重评分沿用原始精度向量。
2. 每页查询最多 4 个点，接收已完成前缀后让出事件循环。首次每点最多取 20 个候选，按本次目标 ID、正文 hash 和去重条件筛选；不足 `q = min(10, N - 1)` 时补查一次，最多再取 40 个。
3. 候选生成阶段保证行号有效、去重和数量充足，索引返回候选 ID 与正文 hash。全部点完成查询后，将矩阵、候选和初解副本转移到 Dream Worker。Worker 直接消费候选，用冻结的原始向量计算相似度，取每点 top-q 的无向并集构建 CSR 稀疏图。
4. 以同组边权之和为目标执行单点移动或两组成员交换，每次接受严格正收益且满足容量的操作。最多执行 3 遍，每点每遍最多参与一次已接受操作。搜索访问上限为 `100 * N * q`，伙伴提示访问另行计数。
5. 优化结束后返回当前分组，核对标签、计数与容量，并映射回完整记忆条目。初始目标值与结束时计算的最终目标值用于诊断记录。

### 执行边界与结果选择

| 项目 | 限制 |
| --- | --- |
| 数值工作集 | 128 MiB |
| 容量二分 | 每个节点最多迭代 3 轮 |
| 候选收集 | 每点首次查询后最多补查一次 |
| 跨组优化 | 最多 3 遍，收益计算的边访问上限为 `100 * N * q` |
| 索引查询让出 | 每页最多 4 个点，完成单点查询后达到 25 毫秒时返回已完成前缀 |

分组各阶段按上述计算边界运行至完成，耗时用于诊断记录。读取、候选查询和算法循环响应取消信号；在途 SQL 完成后交回控制权。诊断中的 `initial` 表示完整容量二分结果，`refined` 表示完成图优化后的合法结果。

ANN 尚未就绪、候选不足或图中全部边权为零时，使用 `initial`。优化达到边访问上限时返回已完整提交操作后的当前分组。输入快照错误、索引主体故障、Worker 故障或取消交由任务结束逻辑处理。

## 工具会话

每个任务持有一份系统提示词、固定工具集合和持续追加的消息历史。公共工具由 `createMemoryTool` 创建，Dream 提供预设、可访问 ID 和处理进度。

| 工具 | 成功处理的目标 | 记忆结果 |
| --- | --- | --- |
| `living_memory_checked_memory` | 指定记忆 | 说明保持原状的理由，并设为已固化 |
| `living_memory_update_memory` | 指定记忆 | 提交完整可变字段与关联用户，更新并固化 |
| `living_memory_merge_memories` | 全部来源记忆 | 至少两条合成一条已固化记忆，归档来源 |
| `living_memory_split_memory` | 来源记忆 | 拆成至少两条已固化记忆，继承来源关系并归档原记忆 |
| `living_memory_delete_memory` | 指定记忆 | 归档 |

可操作 ID 来自已提供的批次和合并、拆分结果，并受预设归属与活跃状态约束。已处理且仍活跃的记忆可以继续更新、合并、拆分或归档；覆盖统计按目标 ID 去重。新增合并、拆分结果加入可访问集合，本次覆盖目标保持启动快照，运行期间新提取的记忆留给后续任务。

每批按以下顺序推进：

1. 从批次中过滤已处理项，跳过空批次，追加其余记忆的完整字段。
2. 在请求前检查历史压缩条件和模型输入容量。
3. 通过 ChatLuna 的 `createOpenAIAgent` 请求一次决策，按返回顺序串行执行工具，并将结果配对写入历史。
4. 本批全部目标处理成功后进入下一批；仍有待办时追加剩余 ID 与反馈，继续本批。

有效 assistant 响应进入历史，包括普通文本、工具调用、推理和签名等元数据。普通文本与执行失败均可作为后续决策上下文。解析失败的响应以转义后的纠错数据进入反馈；换批依据程序维护的处理集合。

每批最多 60 轮，连续 3 轮无有效工具操作时跳过剩余记忆并进入下一批。请求失败、工具全部失败或仅返回普通文本均计为无效轮；至少一个工具调用成功会重置连续无效计数。

## 写入、画像与任务结果

记忆变更经 `LivingMemoryMutationService` 和预设写入队列编排，由 `LivingMemoryRepository` 串行事务提交。更新、合并、拆分的固化随事实一并写入。checked 完成固化后登记覆盖。

事实已经提交而索引同步失败时，工具返回警告并登记处理成功，索引交由后台对账修复。工具参数解析错误及明确的记忆输入错误返回本轮观察结果供模型修正；数据库、索引和内部执行故障结束任务。已提交的事实和覆盖进度始终保留。

遍历完批次后，使用同一模型调用用户画像流程。画像由 `enableUserProfileInjection` 控制，依据当前活跃记忆关联的用户重新生成。批次跳过后仍执行画像阶段，画像供应商请求或输出校验失败记录在任务详情中，内部处理及存储异常进入 Dream 失败处理；任务取消或整理阶段致命中断直接结束。

| 终态 | 条件 |
| --- | --- |
| `completed` | 正常结束且全部目标已处理 |
| `partial` | 正常遍历结束，部分目标已处理且仍有遗漏 |
| `failed` | 存在致命中断，或成功处理的目标数为零 |

任务保存目标数、批次数、覆盖数、遗漏 ID、跳过批次及原因、各工具操作统计和画像详情。后续批次成功处理的早期遗漏会反映到最终覆盖结果中，操作次数单独统计。

服务停止时关闭入口、传递取消信号，等待在途任务结束并记录终态，再释放 Worker 与索引资源。取消检查覆盖准备队列、算法 Worker、模型调用、工具之间和画像阶段。

## 模型输入与上下文压缩

每批通过 `renderMemoriesForModel()` 渲染 ID、类型、正文、摘要、关键词、情绪、重要性、创建与更新时间、用户标签等字段，再进行 XML 转义。可空元数据缺失时省略对应行；保留重要性 0、空关键词和明确的 `speakerLabels=[]`。字段格式见[记忆视图](memory-model-view-plan.md)。

压缩阈值固定为最近一次有效供应商响应的 `usage_metadata.input_tokens >= 200000`，在下一次决策前判断。用量缺失或无效时保留最近一次有效值；首次有效用量上报前仅执行宿主输入容量检查。该阈值采用单次供应商上报，新增批次和工具结果在后续响应中才反映到计数。

压缩通过同一模型的独立摘要请求完成，内容为当前批次之前的历史及已有摘要。摘要记录整理结论、重要关联、约束、失败、待关注事项和必要 ID。压缩后的上下文顺序为：

```text
原系统提示词 → 更早批次摘要 → 当前批次完整字段及本批全部交互
```

摘要成功后清除旧用量基线，等待后续决策响应重新上报。摘要失败、空摘要、首批达到阈值且缺少更早历史，或输入超过宿主声明的可用容量时，结束任务并保留已提交成果。

## 请求与缓存

普通轮次及换批以追加方式维护历史，系统提示词、人设、工具定义与顺序在任务内固定。已发送批次保持原文，新增进度和错误放在历史末尾。压缩替换早期历史，会改变缓存前缀。

请求复用模型公开的 `invocationParams()`、`overrideRequestParams` 和任务 ID；摘要请求使用同一任务 ID 的 `:compression` 后缀。各 adapter 沿用宿主请求构造与用量映射，实际缓存命中由供应商和渠道决定。

历史中的 assistant 副本保留内容和协议元数据，用量通过原始响应单独记录。日志保留供应商返回的输入、输出、推理和缓存明细，缺失项记为“未返回”。

## 运行日志

准备阶段通过 `LivingMemoryLogger.summary()` 输出“事件：中文名称;”及摘要。Dream 开始时显示预设，各准备阶段统一使用单行摘要，字段以分号分隔。向量准备展示记忆数量、向量模型和维度；近邻查询展示覆盖数量与候选数；优化展示图边数、移动与交换次数、组内近邻得分及停止原因；完成摘要展示各批条数与分组总耗时。普通日志耗时以秒为单位并保留三位小数，得分保留两位小数，提升比例保留一位小数；初始得分为零时仅展示前后得分。

准备阶段共输出开始、向量准备、初始分组、近邻查询、分组优化和分组完成六类摘要。采用初始分组时，在完成摘要中说明原因。

## Debug 日志

启用 `debug` 后记录会话系统输入、批次输入、反馈、模型调用、工具结果、轮次进度和人物画像处理。正文采用 `========系统消息========`、`========用户消息========`、`========工具结果========` 等中文分段；异常诊断保留任务、模型调用和批次关联信息。

任务开始、分组准备和批次完成始终显示中文摘要。跳过批次以 WARN 说明原因和处理数量；任务完成、部分完成、失败分别使用 INFO、WARN、ERROR，汇总覆盖数量和各类操作。检查、更新、归档按记忆条数统计，合并、拆分按操作次数统计，归档包含合并与拆分的来源。

压缩日志明确标注压缩前的供应商输入量。模型调用序号统计宿主调用，底层 HTTP 重试次数由宿主或网关日志确认。会话输入只记录新增内容；工具开始由模型工具调用日志体现，工具执行后记录结果。

人物画像处理记录开始与结束摘要，单用户更新或保持原样时记录模型原因；单用户模型请求失败保留警告，画像阶段内部异常交由 Dream 任务入口报告。

## 代码职责

以下路径相对于 `src/service/`：

| 位置 | 职责 |
| --- | --- |
| `workflows/dream/coordinator.ts`、`job_runner.ts` | 触发门槛、预设互斥、后台任务、取消排空与结果落库 |
| `workflows/dream/service.ts` | 准备队列、固定目标、模型、分组、人设、会话与画像衔接 |
| `workflows/dream/clustering.ts` | 向量快照、阶段预算、规划结果与记忆批次映射 |
| `workflows/dream/semantic/`、`workflows/dream/worker/` | 容量二分、候选收集、CSR 构图、跨组修复与 Worker 协议 |
| `workflows/dream/session/runner.ts` | 决策请求、串行工具执行、轮次限制与换批 |
| `workflows/dream/session/state.ts`、`tools.ts` | 可访问范围、处理集合、工具装配、固化与覆盖统计 |
| `workflows/dream/session/history.ts` | 追加历史、用量、容量检查与压缩 |
| `prompts/dream.ts`、`memory_entries.ts` | 系统、批次、反馈、摘要提示词与统一记忆渲染 |
| `memory/tools/`、`app/memory_mutation_service.ts`、`persistence/` | 公共工具、事实事务和索引同步 |
| `vector_index/` | 已有向量读取、近邻候选、索引维护与对账 |
| `user_profile.ts`、`logging/` | 画像生成、模型用量与运行诊断 |

人物画像功能关闭时，Dream 编排直接跳过画像阶段，其查询、模型处理、阶段日志及关闭说明一并跳过。

Dream 会话开始摘要仅展示预设，随后保留完整系统消息正文。
