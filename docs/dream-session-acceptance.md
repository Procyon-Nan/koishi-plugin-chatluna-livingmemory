## 三类协议的实际 HTTP 请求

使用安装中的 ChatLuna adapter，连接仅监听 `127.0.0.1` 的临时 HTTP 服务，接收实际序列化请求并返回协议响应。这里的模型决策与 usage 都是模拟数据，不是供应商端到端验收。

每个场景使用现有数据中的 31 条记忆分成 30、1 两批，暴露相同的六个公共工具。首轮返回两个 checked 调用并由程序串行执行，下一轮完成第一批，第三轮完成第二批；checked 经仓库写入独立 SQLite 副本。四个场景均覆盖 31/31，六个工具定义、系统内容及此前消息前缀逐请求保持一致。

| 场景 | 实际请求检查 | 响应元数据检查 |
| --- | --- | --- |
| Gemini | 系统与工具不变，跨轮、跨批次追加历史 | functionCall 的 thoughtSignature 回传；模拟缓存计数正确到达日志 |
| OpenAI-compatible，setCacheKey 开启 | 每次 prompt_cache_key 都等于固定会话 ID | 工具调用/结果链正常，模拟缓存计数正确到达日志 |
| OpenAI-compatible，setCacheKey 关闭 | adapter 不发送 prompt_cache_key | 会话仍完成，不强行覆盖 adapter 的配置 |
| Claude Messages | 显式 overrideRequestParams 中的 cache_control 原样传入；宿主内部仍采用 SSE | thinking/signature 回传；当前宿主丢失分段 usage 的输入和缓存明细，见下文 |

Claude 的本地 HTTP 服务在 `message_start` 返回输入量及缓存读取/创建量，在 `message_delta` 仅返回输出量。当前 ChatLuna 的 `StreamMetricsTracker.observe()` 将 usage 替换成最后一段，随后 `ChatLunaChatModel._generate()` 用这份结果覆盖最终消息的 usage，导致输入量与缓存明细丢失，并可出现非有限的 total。LivingMemory 没有重新计算或补造这些数字。

此限制位于 ChatLuna，遵守本次“不能修改 ChatLuna”的边界，未修改宿主，也未在插件里增加流式统计兼容层。它影响缓存计数的可观察性；在供应商用量作为唯一压缩依据后，输入上报缺失也会使阈值压缩无法触发。这不是 Claude 请求不能缓存的证据；真实 Claude 端点能否接受指定缓存参数尚未验证。

## 200k 压缩

在 `8d3d07f` 基线上，通过真实 ChatLuna tokenizer、OpenAI-compatible adapter 和本地 HTTP 摘要响应检查了当时的压缩路径，没有修改阈值或伪造 token 计数：

- 构造更早批次的长历史，当前批次使用现有 30 条记忆的完整渲染结果，并附带 assistant 工具调用、工具结果和进度消息。
- 压缩前计数 355,662，达到固定的 200,000 阈值；摘要后为 5,675。
- 摘要请求只收到更早批次，使用独立的 `protocol-compression:compression` 缓存键。
- 当前 30 条记忆的完整渲染文本、工具调用、签名元数据、工具结果和进度消息均保留；系统消息未改写。

以上验证宿主 tokenizer 的实际计数、请求序列化和历史替换逻辑；摘要由本地服务返回，不能作为真实模型摘要质量或压缩后缓存命中的证明。

真实运行同时发现明显的计数偏差：第 9 次调用前宿主估算为 16,731，供应商返回的 input 为 46,978；第 10 次调用前估算为 21,664，供应商返回的 input 为 58,076。该基线的 200k 因而是宿主估算阈值，不能等同于供应商实际输入阈值。宿主计数使用统一消息格式，不计全部 adapter 元数据；供应商 tokenizer 和内部计数也可能不同，本次没有将差值全部归因于某一个原因。用户已确定“始终以供应商返回的为准”，现已修正为以下口径。

- 仅记录决策响应中有效的 `usage_metadata.input_tokens`，达到 200,000 后在下一轮决策前压缩；不使用累计消耗、输出量、本地估算，也不额外累加缓存计数。工具先执行完毕，随后才压缩或换批。
- 缺失、非有限或非正值不覆盖最近有效上报；没有有效上报时不能触发阈值压缩。宿主计数只用于主会话与摘要请求的模型容量检查，超限时报错以避免静默裁剪，不参与 200k 判断。
- 成功压缩后清除旧用量，等待下一次决策上报；摘要调用的用量与保留历史中的旧 usage 不作为新上下文大小。当前批次及全部交互仍原样保留。
- 会话回归用例通过：199,999/200,000 边界、长文本与缓存明细不改变阈值、压缩失败保留历史与有效用量、压缩后清除旧基线、解析失败响应仍记录用量并正确压缩。用量由测试注入，不能当作真实供应商达到 200k 的验收。

- 用量修正仅涉及 LivingMemory 会话历史、响应回调及相应测试和文档，没有修改 ChatLuna。本次 `yarn lint`、`yarn atsc -p tsconfig.json --noEmit`、`yarn test`（45 个文件、367 个用例，含 11 个会话用例）及 diff 检查通过；审查未发现待修复的重要问题。此前完整 Dream 的真实运行结果不代表本次修正后的重新运行。
